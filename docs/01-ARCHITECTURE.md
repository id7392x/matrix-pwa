# 01. Архитектура системы  
**Версия:** 2.1-ARCHITECTURE    
**Статус:** Основной архитектурный документ    
**Подчиняется:** `00-PRINCIPLES.md`  
  
Этот документ описывает высокоуровневую архитектуру клиента. Детали хранения данных и эталонный код вынесены в отдельные документы.  
  
---  
  
## 1. Слои и поток данных  
  
Система строго разделена на четыре слоя:  
  
  
UI Layer (Svelte 5)  
↑↓  только DTO + команды  
Domain / Application Layer  
↑↓  DTO  
Matrix Client Layer (matrix-js-sdk + Rust Crypto)  
↑↓  
Persistence Layer (Dexie.js + Cache Storage)
  
### Основные ответственности Domain / Application Layer  
- `AccountManager` — управление аккаунтами, Active/Lazy, переключение  
- `SyncOrchestrator` — координация синхронизации и фильтров  
- `PendingQueueService` — оптимистичные сообщения и dual-path promote  
- `BatchedStoreManager` — пакетная доставка обновлений в UI  
- Преобразование сырых объектов SDK → плоские DTO (единственное место, где это разрешено)  
  
### Главный поток данных (входящий)  
1. Matrix Client Layer получает события через `/sync`.  
2. Domain Layer преобразует их в DTO.  
3. DTO проходят через `BatchedStoreManager`.  
4. UI Layer реактивно отображает данные.  
  
### Главный поток данных (исходящий)  
1. UI отправляет команду.  
2. Domain Layer создаёт оптимистичную запись через `PendingQueueService`.  
3. После подтверждения сервера (ответ `/send` **или** эхо из `/sync`) выполняется атомарный promote pending → synced.  
  
**Критическое правило:** Классы SDK никогда не пересекают границу Domain → UI.

## 2. Multi-account архитектура  
  
Система поддерживает несколько аккаунтов одновременно.  
  
### Роли аккаунтов  
  
| Тип              | Поведение                                                                 | Синхронизация                  |  
|------------------|---------------------------------------------------------------------------|--------------------------------|  
| **Active**       | Текущий выбранный пользователем аккаунт                                 | Непрерывный `/sync`            |  
| **Lazy**         | Фоновые аккаунты                                                         | Polling 2–5 мин + мгновенный sync при фокусе/переключении |  
  
### Правила  
  
- В каждый момент времени только один аккаунт является Active.  
- Переключение аккаунта не требует перезагрузки страницы.  
- Lazy-аккаунты используют узкий filter, но **обязаны** получать критические `to_device`-события (см. Principles §3.3.2).  
- Каждый аккаунт имеет полностью изолированный crypto store и собственный контекст клиента.

## 3. Multi-tab архитектура (Single Active Tab)  
  
Для предотвращения гонок записи в IndexedDB и повреждения crypto store используется модель **Master / Slave**.  
  
### Механизм  
  
- Используется **Web Locks API** (`navigator.locks`).  
- Имя лока: `matrix_master_${userId}_${deviceId}`.  
- Первая вкладка, получившая лок, становится **Master**.  
- Остальные вкладки становятся **Slave**.  
  
### Обязанности ролей  
  
**Master-вкладка:**  
- Держит активный `/sync`  
- Инициализирует и использует Rust Crypto  
- Выполняет все записи в IndexedDB, связанные с синхронизацией  
- Рассылает обновления через `BroadcastChannel`  
  
**Slave-вкладки:**  
- Работают в режиме чтения из IndexedDB  
- Отображают UI  
- Проксируют пользовательские действия (отправка сообщений и т.д.) в Master через `BroadcastChannel`  
- Показывают баннер «Приложение открыто в другой вкладке» при необходимости  
  
### Поведение при сбоях  
  
- При закрытии или краше Master-вкладки браузер автоматически освобождает лок.  
- Одна из Slave-вкладок получает лок и становится новым Master.  
- При обновлении Service Worker (`controllerchange`) необходимо корректно сохранять контекст лока.  
  
### Безопасность и надежность межвкладочного канала (BroadcastChannel)  
 Для защиты от XSS и несанкционированного управления все сообщения между вкладками подписываются сессионным одноразовым токеном (`handshake/nonce`), генерируемым Master-вкладкой.  
 При отправке команд из Slave в Master (например, отправка сообщения) Slave ожидает подтверждения получения (`ACK_PENDING`) в течение 500 мс.  
 Если Master не прислал `ACK_PENDING` (краш или зависание Master), Slave повторно инициирует проверку Web Lock, перехватывает роль Master и выполняет команду самостоятельно.  
### Синхронизация состояния между вкладками  
 Master пишет актуальные данные в IndexedDB и дополнительно рассылает важные обновления через `BroadcastChannel`.  
 Slave-вкладки читают данные из IndexedDB и подписываются на `BroadcastChannel` для получения оперативных обновлений.  
 Запрос `accessToken` от Slave к Master происходит по защищенному Handshake-протоколу через `BroadcastChannel` только в оперативную память (RAM) без сохранения в хранилища.  
 При переключении роли (Slave -> Master) новый Master обязан заново инициализировать crypto и синхронизацию по Cold Start Protocol.  
  
### Несколько аккаунтов и несколько вкладок  
Лок берётся отдельно для каждой пары `userId + deviceId`. Разные аккаунты могут иметь своих Master-вкладок одновременно.

## 4. E2EE и криптографический слой  
  
### Движок  
Используется официальный Rust WASM crypto (Vodozemac) через `matrix-js-sdk`.  
  
### Изоляция  
Каждый аккаунт + устройство имеет свой изолированный store:  
```ts  
cryptoDatabasePrefix: `matrix-js-sdk:crypto:${userId}:${deviceId}`  
```

### Cold Start Protocol  
Строгая последовательность (см. Principles §3.3.1):  

1. `createClient()`  
2. `await initRustCrypto({ cryptoDatabasePrefix })` — полная загрузка WASM и восстановление сессий  
3. Только после этого — `startClient()`  
  
Любая обработка событий до завершения `initRustCrypto` запрещена.  
  
**Модель Unable To Decrypt (UTD) и Re-decryption**  

| Тип | Причина | Поведение UI | Таймаут / Поведение |
| ------------- | -------------------------- | --------------------------------- | -------------------------------------- |
| Temporary UTD | Ключ еще не пришел | Индикатор ожидания / запрос ключа | Авто-запрос ключа (m.room_key_request) |
| Permanent UTD | Ключ утерян или не передан | Плашка «Не удалось расшифровать» | Срабатывает через 30 сек без ответа |
  
**Механизм реактивной перерасшифровки (Re-decryption):**  
* Переход в Permanent UTD через 30 секунд не является окончательным блоком.  
* Domain Layer подписывается на событие поступления новых ключей шифрования в Rust Crypto.  
При получении недостающего ключа Domain Layer автоматически запускает повторный проход расшифровки (Re-decryption) для событий со статусом UTD и обновляет их DTO в BatchedStoreManager.  
  
### Дополнительно  
- Поддержка Cross-Signing  
- Верификация устройств через SAS (эмодзи) и QR  
- Recovery Key: при отсутствии ключа показывается ненавязчивый баннер

## 5. Сетевой слой  
  
Сетевой слой полностью изолирован за интерфейсом `ISyncProvider`.  
  
- Текущая реализация: `LegacySyncProvider` (классический `/sync`).  
- Архитектура позволяет заменить его на `SlidingSyncProvider` (MSC3575) без изменений в Domain, Persistence и UI.  
  
Фильтры синхронизации формируются в Domain Layer (`SyncOrchestrator`).    
Для Lazy-аккаунтов filter обязан соответствовать инварианту из Principles (критические `to_device`-события не должны отрезаться).  
  
---  
  
## 6. Управление состоянием UI  
  
### BatchedStoreManager  
Все входящие обновления из сети накапливаются в буфере и сбрасываются пакетами:  
  
- Активная вкладка → `requestAnimationFrame`  
- Фоновая вкладка → `setTimeout(0)` + обработка `visibilitychange`  
  
Прямая запись событий синка в `$state` запрещена.  
  
### DTO-граница  
Перед попаданием в сторы все данные преобразуются в плоские DTO.    
DTO содержат только данные, необходимые для отображения (включая `aspect-ratio` для медиа, чтобы избежать layout shifts при виртуализации).

## 7. Безопасность (сводка)  
  
Основные защиты:  
  
- *`accessToken`* — только RAM или *`sessionStorage`* (никогда в IndexedDB/localStorage); *`refreshToken`* — единственное исключение, в `accounts.refreshToken` (Principles §3.2.2, Слайс 4)
- Полная изоляция crypto store по *`userId + deviceId`*
- Одна Master-вкладка на устройство (Web Locks)  
- Статическая схема базы данных  
- Запрет сырых объектов SDK в UI-слое  
  
Рекомендуемый CSP:  
  
default-src 'self';  
script-src 'self' 'wasm-unsafe-eval';  
worker-src 'self' blob:;  
connect-src 'self' https: wss:;  
object-src 'none';
